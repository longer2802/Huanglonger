# 菜單掃描器（Menu Scanner）規格

（以下為原始需求）

一、專案目標與限制
這是一個獨立的菜單掃描工具。使用者選擇或拍攝台灣飲料店、便當店的菜單照片後，App 要讀出「品名、規格、價格」，整理成可編輯的表格。確認後可複製文字、下載 TXT／CSV，或透過 iOS 分享面板分享檔案。優先把台灣手搖飲料菜單做穩，同時支援單一價格的餐點菜單。
使用 SwiftUI、Apple Vision、PhotosUI 及必要的 Apple 原生框架。以 iOS 17 以上為第一版目標。照片、辨識、解析、儲存和匯出均在裝置上完成。不要加入後端、帳號、API Key、付費 OCR、雲端 AI、遙測或訂閱。掃描流程不得依賴網路。
第一版範圍限掃描、校對、匯出、店家菜單庫。點餐、收款及多人協作留在原本的辦公室揪訂 App。

二、手機操作流程
1. 首頁：主要按鈕「拍攝菜單」「選擇照片」；次要入口「貼上文字」「店家菜單庫」。真機可拍照，模擬器保留選照片與測試圖入口並依實際能力顯示拍照狀態。載入後可預覽、旋轉與裁切，提示使用者將整張菜單拍清楚，尤其是價格表頭。
2. 辨識：支援整張辨識及手動框選單欄重掃。顯示處理中、成功、找不到可讀內容及錯誤等狀態，可取消或重試，OCR 不得阻塞畫面。支援原況文字貼入的純文字；沒有座標且杯型價格無法可靠配對時標記待確認。單欄重掃只更新所選區域的候選結果，保留範圍外資料及已確認或手動修改的內容；有衝突先顯示差異供選擇。
3. 校對：原圖／表格切換；點選有來源座標的資料時顯示原圖對應位置。每列欄位：分類、品名、規格、價格、待確認狀態，可修改、新增、刪除，同一品名可新增多個規格。提供「只看待確認」並說明原因（如「價格與上一列重疊」「有兩個價格但找不到杯型表頭」「品名疑似錯字」）。空白或「—」表示未供應的杯型，確認語意後略過；看不清楚的價格保持空白，不能自動補 0。可儲存草稿。正式匯出時若仍有待確認項目，顯示清單讓使用者修正或明確選擇只匯出已確認品項，不可默默帶入未確認價格。

三、辨識及價格配對
1. Vision OCR：VNRecognizeTextRequest accurate 路徑，依實際 revision 檢查可用語言，優先 zh-Hant、其次 en-US。保留原始文字、候選文字、信心分數及 bounding box；統一處理照片方向、裁切與 Vision 座標轉換，確保高亮位置正確。先以正常影像辨識並保留足夠解析度；重掃時可提供局部對比增強，並讓使用者看到目前使用的圖像範圍。
2. 結構解析：OCR 與解析分開，解析器可用固定 OCR 結果獨立測試。先找左右欄或品項區，再用區域內垂直位置配對品名與價格，隔壁欄數字不得跨欄配對。支援單價格、M／L、中杯／大杯及明確標示的容量欄；依表頭及座標確認規格，支援表頭從大杯排到中杯。只有「55／65」又無明確表頭時保留兩個候選價格並標待確認。正規化全形價格、NT$、$、元；容量 500ml、電話、分店地址、活動日期不可當售價。加料、套餐、促銷價若無法確定適用範圍，放待確認區，不覆蓋基本價格。排除獨立的甜度、冰量表、著作權、聯絡資訊，依整行文字與區域判斷，避免誤刪品名。提供可測的常見誤字詞庫（如「憲桃→蜜桃」「拿錢→拿鐵」），校對畫面顯示建議與原文讓使用者選；價格配對不明時留空並提示，禁止推測。資料模型為「一個品名＋一種規格＋一個價格」一筆，區分同名不同杯型，保留原圖、原文與使用者修改的對應。

四、店家菜單庫與匯出
- 本機儲存；每份菜單含店名、分店（選填）、分類（飲料／餐點）、校對日期、原圖及已校對品項。
- 可搜尋店名或分店、開啟校對、另存新版及匯出；可從舊版編輯新稿，舊版仍可查看。
- 內建一份清楚標示「示範」的虛構飲料菜單，涵蓋單價、中／大杯與缺某杯型的品項。
- TXT 用 UTF-8，每行一筆，例如「蜜桃烏龍｜大杯｜65 元」，提供一鍵複製。
- CSV 用 UTF-8，預設欄位「店家,分店,分類,品名,規格,價格」；價格只輸出整數；逗號、引號、換行依 CSV 規格轉義。
- 若 workspace 已有「辦公室揪訂」菜單匯入規格，讀取並提供相容匯出；否則交付上述格式與範例檔，README 說明欄位對應。
- TXT／CSV 使用 iOS 分享面板，檔名含店家、分店及校對日期。

五、測試與 90% 驗收
自動化測試至少涵蓋：單價格便當菜單；左右欄相鄰且出現相同價格的飲料菜單；中杯／大杯順序反轉、品名換行、缺少某規格、價格模糊或無法配對；不把電話、容量、促銷價、甜度冰量表誤當售價；詞庫修正保留原文；重掃單欄後保留其他欄與手動確認結果；繁體 TXT／CSV、含逗號與雙引號的品名；重開 App 後仍能載入菜單。
建立可重跑的基準測試：讀入菜單圖片與人工標準答案，輸出每張圖的正確、漏抓、多抓、待確認筆數及處理時間。每個規格獨立算一筆，品名、規格、價格三欄完全相符才算正確，同一筆標準答案只配對一次；待確認或人工改正的筆數不計入自動正確數。
正式驗收用 20～30 張實際菜單（截圖、手機實拍、多欄、大小杯分欄），保留一批未用於調規則的菜單。目標：正確數÷標準答案數 ≥ 90%，且正確數÷App 自動判定完成數 ≥ 90%，分版型列出結果。沒有真實菜單時，先用明確標示的合成範例驗證流程，並建立放入真實圖片與標準答案的方式；不得以合成資料宣稱達到 90%。

六、完成與交付
實際完成 SwiftUI 畫面、Vision 掃描、解析、校對、儲存、店家庫及匯出。用 xcodebuild 執行編譯和測試並處理可重現的失敗；用模擬器走一次選圖→辨識→修正→存入店家庫→匯出。README 說明如何在 Xcode 開啟、啟動模擬器、安裝到 iPhone、跑基準測試、解讀兩項指標、將 CSV 匯入辦公室揪訂。最後回報完成的功能、專案位置、實際測試結果、準確率是否經真實菜單驗證、仍待實機確認的項目。

# 執行補充（優先遵守）
1. 分四階段進行，每階段結束須 xcodebuild 編譯與測試全數通過，回報結果後再進下一階段：
   ① 專案骨架＋資料模型＋OCR 服務＋解析器與單元測試
   ② 首頁、辨識流程、校對畫面、TXT/CSV 匯出
   ③ 店家菜單庫（SwiftData）、版本、單欄重掃與差異合併
   ④ 基準測試工具、README、範例 CSV
2. 專案用 XcodeGen 產生（project.yml），若未安裝可用 brew install xcodegen；不要手寫 .pbxproj。
3. CSV 一律輸出 UTF-8 with BOM，確保 Excel 開啟不亂碼。
4. 基準測試資料放在 Benchmarks/menus/（圖片）與 Benchmarks/answers/（同名 .csv 標準答案），README 說明格式。
5. 解析規則盡量與 UI 解耦放在獨立模組，方便日後用真實菜單反覆調整。
